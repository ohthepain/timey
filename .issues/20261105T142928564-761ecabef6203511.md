## Agreed outcome

Offer cleanup at explicit issue closure, rather than automatically at PR merge. The close dialog lists separate options for deleting the GitHub branch, deleting the local branch, removing the issue workspace, and archiving associated chats. Default to attempting eligible cleanup. Display the repository and exact branch names, full workspace paths and estimated recoverable storage, and exact affected chats before submission.

Check remote and local resources separately. If a branch is already deleted, disable its checkbox, grey its name and show Already deleted. A failed lookup is an unknown/error state, never proof of deletion. Recheck immediately before acting so manual GitHub deletion and repeated requests remain safe.

Preserve unfinished work, unsaved files, work used by another issue, and active workspaces/chats. Explain every retained resource. Closing without an accepted fix preserves unmerged work by default. No forced reset, discard or broad deletion is implied by the default cleanup choices.

Before workspace removal, preserve the issue history, PR relationship, required verification evidence and acceptance records in durable project storage outside that workspace. Workspace-local dependencies, build output and disposable caches may be removed with the owned workspace. Shared caches and retained history require a separate policy; they are not swept up by this operation. Archiving chats is sidebar cleanup, not a claimed disk-space saving.

Issue closure and cleanup success are separate results. Complete otherwise valid explicit closure even if cleanup fails; display Cleanup incomplete, per-resource results, useful reasons and Retry cleanup. Retrying is bounded to the selected issue's retained cleanup record and starts no implementation or merge. Existing verification and human acceptance requirements for Fixed closure remain unchanged.

## Approved addition: isolated starting point and one owning branch

The user approved adding this requirement to this same report: "yes let's add that to the issue" after the recommendation to start every new issue from freshly checked dev, keep all repairs on its own branch, and require a deliberate choice before including another issue's unfinished work.

For new issue work, fetch the configured remote target (dev in this project), resolve and record its exact commit, and create the issue's dedicated branch and workspace from that commit. Do not inherit the main checkout's current branch or local unpublished commits implicitly. If the remote target cannot be fetched or verified, stop with an actionable explanation rather than silently using another starting point. Preserve the main checkout and its existing work.

Keep implementation, necessary test/audit repairs and conflict resolution on the issue's same owning branch and workspace through its PR. Updates already merged into the target may be brought into that branch normally; they are not accidental inclusion of another issue's unfinished work. Introducing unfinished work from another issue requires an explicit choice naming the dependency, exact included commits and reason. Do not copy changes to replacement branches as a routine recovery mechanism.

For existing work and Continue, preserve the original branch, base, history and evidence. Verify ownership and reconcile the actual PR state before doing more work. Do not reset existing work or silently recreate its branch from the current target to satisfy this new-start policy. Explain inherited unrelated work and offer an explicit safe decision where needed.

Additional verification: start a new issue while the main checkout is on a different issue branch, contains unpublished commits, or has unsaved changes; confirm only the freshly fetched target is used and existing work remains untouched. Cover fetch failure, explicit dependency inclusion, ordinary target updates, retained existing work on Continue, and repairs remaining on the owning branch. These additions do not change merge style or authorize implementation, publication, closure or deletion now.
