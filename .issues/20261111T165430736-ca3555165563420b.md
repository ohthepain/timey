## Original request

> let's write this up as an issue and as a design. track the reports on the target branch (normally dev), keep the workspaces local, and use a remote claim branch so two runners can't pick up the same issue. a worker claims an issue by creating a branch with a certain naming convention. if creating the branch wasn't successful then the worker can begin progress. so the work stays local and the issue queue is shared on the target branch. updating the queue requires a push to the target branch, so it should only really happen in very specific circumstances, such as when the issue is created or closed or progress is ended, or work must be handed off

## Proposed behavior

A runner starts only after it confirms it created and owns the issue's remote claim. This draft reads the sentence about unsuccessful creation as a slip, consistent with the requested exclusive ownership.

Version-control the issue list as `.issues/<full-issue-id>.md` reports on the configured target branch, normally `dev`. Share `.issues/issue-numbers.json` to preserve display numbers. Keep `.issues/issue-work/` ignored by Git on every clone. Use a target checkout for queue operations and an issue worktree for execution. Publish report changes at creation, closure, end of Progress, and explicit handoff.

See the [draft design](../docs/plans/shared-issue-queue.md) and [proposed ADR](../docs/adr/0011-share-issue-reports-on-the-target-branch.md).

## Acceptance criteria

- Two runners sharing a remote can read the same published queue, and only one can start a given issue.
- Routine progress stays local. Publication at the defined milestones requires human PR review and preserves concurrent changes.
- A fresh target checkout contains the reports and display-number registry. Migrated reports retain their full IDs and history. Files created under `.issues/issue-work/` remain ignored and never appear in the target branch.
- An interrupted claim, failed checkpoint, or delayed release cannot start duplicate work or remove another run's claim.

## Routing

This is an enhancement with no existing failure to reproduce. The design records the agreed publication policy. The implementation is committed locally. Live rollout and acceptance are pending.

## Decisions

If a required report checkpoint fails to publish, retain the pending update and claim. A human must reconcile the failure before release.

Shared report updates require a human-reviewed PR. The factory can prepare a queue-only PR or include the report in a code PR that receives human review. Remote claims take effect immediately. The claim stays held until the required report update lands.
